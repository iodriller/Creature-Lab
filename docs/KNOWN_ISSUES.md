# Known Issues

Latent gaps and deliberate limitations found during code review, tracked here so they
aren't lost and don't need re-discovering. Update this table in the same change that
fixes or knowingly accepts an item — see [`CHANGELOG.md`](../CHANGELOG.md) for what has
already shipped.

| Item | Area | Status | Notes |
| --- | --- | --- | --- |
| Diagnosis is not terrain-aware | `diagnosis.py` | Open (low priority) | `com_height_std` and the upright/fall check are calibrated for flat ground. A creature climbing a steep or long `slope`/`steps` terrain will show rising/falling CoM height and could false-flag `com_instability` even when the gait is healthy — the signal doesn't currently subtract the terrain height profile at the root's (x, y). Not observed at today's zoo task magnitudes (`slope_angle<=0.15`, `step_height<=0.05`); worth fixing before adding steeper terrain tasks. |
| Non-flat terrain has a finite 6.4 m extent | `terrain.py`, `validation.py` | Partially closed | The heightfield grid is `DEFAULT_ROWS x DEFAULT_COLS x DEFAULT_CELL_SIZE` = 64×64×0.1 m, centered at the origin; a creature can walk off the edge with no ground beyond it. `validate_episode_inputs` now warns when a **target** lies outside that extent on non-flat terrain (a concrete, checkable case). It cannot warn for target-less locomotion tasks (e.g. `crawl_forward`-style) since there's no way to predict expected travel distance from the spec alone — that part stays open. |
| Terrain grid assumes `rows == cols` | `terrain.py` | Closed | `flatten_for_heightfield_api`'s row/column convention was verified empirically (a PyBullet raycast probe, a MuJoCo free-falling probe body) only for a **square** grid. `terrain.py` now asserts `DEFAULT_ROWS == DEFAULT_COLS` at import time, so changing the constants to a non-square shape fails loudly instead of silently swapping which world axis the terrain varies along. |
| CI does not build or install-test the wheel | `.github/workflows/ci.yml` | Closed | CI now builds the wheel, installs it into a fresh venv, and runs `doctor` + `zoo run` against the installed package (not the checkout) on every push/PR — the same check Phase 5 ran by hand. |
| MuJoCo's default actuator/friction export makes locomotion much weaker than PyBullet for the same open-loop gait | `export/mjcf.py`, `backends/mujoco_backend.py` | Open (low priority) | Found while adding the `target_seek` controller: `generate_quadruped()` under the CPG gait travels ~0.07 m in 3 s on MuJoCo vs. ~0.5-0.9 m on PyBullet for the same creature/task — a much bigger gap than typical sim-to-sim divergence. A steering/reach-target scenario that reads cleanly on PyBullet is not currently a reliable signal on MuJoCo because the body barely translates regardless of controller. This is the existing "physics is backend-dependent" limitation below, just unusually severe for this creature/gait pair — likely fixable by tuning the exported MJCF actuator gains, not by anything controller-side. |
| The fake-GUI test harness can't catch a real Mantine/browser rendering crash | `tests/test_editor_controls.py`'s `_FakeGui` | Closed with layered coverage | `scripts/browser_smoke.py` drives the real first-run journey, asserts client errors stay empty, and verifies the server port closes; a dedicated browser CI job installs Chromium and runs it. The fake GUI remains useful for fast structural tests but is not treated as browser proof. |
| PyBullet silently mismatched branched link identities | `backends/pybullet_backend.py` | Closed | The backend submitted links breadth-first, while PyBullet canonicalized the resulting tree depth-first. On a multi-level branched body, `link_names`, joint commands, contacts, and traces could therefore refer to different physical links; shallow creatures hid the defect. Link construction now follows depth-first tree order, with a regression test that checks symmetric humanoid feet and joint identity. |
| Onboarding rewards scored a successful run negative | `editor/presets.py` task rewards, `scoring.py`, `editor/controls.py` result headline | Closed | Measured every onboarding creature x goal x controller combo through real physics and found the root cause: `reach_target`'s `energy_penalty=0.01` was ~10x too high relative to the actual raw energy accumulated in a few seconds of open-loop actuation (~100-280 units, measured), so it swamped the target reward and made a run that reached 83% of the way to the target score **-0.10**. `stability_hold` was built only from penalties (`fall_penalty` + `energy_penalty`), so its best possible score was 0 — a creature that stayed up the whole episode could never score positive. Fixed by (1) lowering `energy_penalty` to 0.001 across the onboarding presets (empirically re-measured to leave real progress positive for every preset creature), (2) adding `RewardSpec.survival` (the positive mirror of `fall_penalty`: reward for still being upright) and wiring `stability_hold` to use it, and (3) reframing the Result headline to lead with concrete progress ("Moved 0.83 m closer to the target; stayed upright") with the raw score shown below it, not as the sole headline. Every onboarding creature now scores positive on every goal it visibly succeeds at. |
| Humanoid had no credible walking result | `scaffold/humanoid.py`, `controllers/factory.py`, Zoo/editor presets | Closed for the scoped PyBullet baseline | The earlier conclusion that every nonzero gait necessarily failed was measured on a broken model: branched PyBullet link identities were mismatched, the feet were vertical capsules, segment masses summed to 75 kg despite a requested 60 kg, and every motor shared a 5 N·m force cap. The corrected 12-DOF model has horizontal box feet, normalized mass, per-motor 160 N·m limits, center-offset gaits, and a packaged measured controller. It travels about **0.417 m in 5 s without falling** on PyBullet and survived a 30 s validation run. It is a slow open-loop stepping/shuffling baseline, not a robust learned gait; on MuJoCo it stays upright but moves about 0.066 m backward, so the controller is explicitly PyBullet-tuned. The footless `humanoid_minimal` remains a challenge. |
| No humanoid active roll (side-to-side) balance DOF | `scaffold/humanoid.py` | Open | Generated humanoid hip/knee/ankle hinges use `axis=[0,1,0]` (sagittal-plane only), so `PostureController` can correct pitch but not roll. With the corrected horizontal-foot stance, posture survives measured forward and backward 3000 N pushes and a 3500 N lateral push, but a 4000 N lateral push topples it. The walking gait likewise accumulates lateral drift: it remains upright at 30 s but fell near 59 s in a 60 s run. A real fix needs hip ab/adduction joints, roll feedback, and a newly qualified gait. |
| `PolicyController` reaches into `CreatureEnv`'s underscore-prefixed methods | `controllers/policy.py` | Mitigated, accepted trade-off | Reusing the exact transforms prevents training/inference drift. Policy ControllerSpecs now record observation/action specs and creature/task hashes, and loading checks model-space dimensions before simulation; older bundles without ABI metadata remain less trustworthy. |
| A trained `policy.zip` is not guaranteed to load across Stable-Baselines3/torch versions | `rl/train.py`, `controllers/policy.py` | Open (low priority) | SB3's `PPO.save()`/`PPO.load()` round-trip is a pickle-based format tied to the SB3/torch versions used to train it - unlike `controller.json`'s other types (plain JSON numbers, always portable), a `policy`-type controller bundle can fail to load if moved to an environment with a materially different `rl` extra version. Not observed in this session's testing (single environment throughout); worth a compatibility note in `docs/CLI_REFERENCE.md` if this becomes a real support burden. |

## Deliberate, accepted limitations (not bugs)

These are documented design choices, not gaps to close:

- **Exact physics is backend-dependent.** PyBullet and MuJoCo simulate the same
  `CreatureSpec`/`TaskSpec` with different solvers/contact models; scores and trajectories
  can differ substantially for the same open-loop gait (see `sim2sim`, and the packaged
  `baselines/<task>.mujoco.json` vs. `baselines/<task>.json` pairs). This is the stated
  portability contract, not something to eliminate.
- **`gaps` terrain uses a deep pit (`-10.0 m`), not a true hole.** Neither backend's
  heightfield primitive supports an actual discontinuity in the ground; a very deep pit is
  a good-enough stand-in for "impassable" at creature scale.
